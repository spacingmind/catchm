# Plan: M3.5 — translate setup/health endpoints (backend only)

- Status: complete
- Created: 2026-09-18

## Goal

M3 wired an `OllamaTranslator` into pipeline/batch, but a user has no way
to find out whether Ollama is running, whether the configured
TranslateGemma model is actually pulled, or whether the translation
prompt/model even works — before relying on it in a real meeting. This
milestone adds backend-only endpoints for that: status check, one-click
model pull with progress, and a text test call. No UI in this
milestone — verify with curl/httptest; a future web UI milestone wires
buttons to these.

Confirmed real-world facts to build against (verified against Ollama's
actual API, not placeholders): `translategemma:4b`/`:12b`/`:27b` are real
pullable tags; Ollama's default API is `http://127.0.0.1:11434`
(matches `internal/config`'s existing default host).

## Scope

- `internal/translate/ollama.go` (same package as `OllamaTranslator`):
  - `ListModels(ctx context.Context, host string) ([]string, error)` —
    `GET {host}/api/tags`, returns the `name` field of each entry in
    `models`. A connection failure (Ollama not running) returns a
    wrapped error the caller can distinguish from "reachable but model
    missing" — export a sentinel `var ErrOllamaUnreachable`.
  - `Pull(ctx context.Context, host, model string, onProgress func(status string)) error` —
    `POST {host}/api/pull` with `{"model": model, "stream": true}`,
    reading the NDJSON response line by line and calling `onProgress`
    with each frame's `status` field (e.g. `"downloading 42%"`,
    `"success"`) as it arrives — this is a streaming callback, not a
    buffered return, because the caller (the HTTP handler) forwards each
    line to its own client as it happens. Returns an error if any frame
    has a non-empty `error` field, or on a non-2xx response.
- `internal/server`: three new endpoints, using swappable fields for
  testability (same seam pattern as `newEngine`/`newTranslator`):
  - `GET /api/translate/status` — calls `ListModels` against
    `cfg.Translate.Host`. Response:
    ```json
    {
      "ollama_reachable": true,
      "live_model": {"name": "translategemma:4b", "installed": true},
      "batch_model": {"name": "translategemma:12b", "installed": false}
    }
    ```
    When Ollama is unreachable, `ollama_reachable: false` and both
    `installed` fields are `false` — this is not an HTTP error, it's a
    valid status payload (200), since "not set up yet" is an expected
    state, not a server fault.
  - `POST /api/translate/pull` — body `{"target": "live"|"batch"}`
    (maps to `cfg.Translate.LiveModel`/`BatchModel`; 400 on any other
    value). Streams the underlying NDJSON `Pull` progress straight
    through to the HTTP response body (`Content-Type:
    application/x-ndjson`, flush after each line via `http.Flusher`) so
    a future UI can read it incrementally. On a `Pull` error mid-stream,
    write one final `{"error": "..."}` line rather than changing the
    HTTP status (headers are already sent by the time streaming starts).
  - `POST /api/translate/test` — body `{"text": "...", "target_lang":
    "...", "target": "live"|"batch"}` (target defaults to `"live"`).
    Builds a `Translator` via the existing `newTranslator` seam for the
    resolved model and calls `Translate` once, returning
    `{"translated": "..."}`. 400 if `text` or `target_lang` is empty;
    502 if translation fails (distinguish from the app's own bad-request
    errors).

Out of scope: any UI/frontend, persisting pull progress across restarts,
concurrent-pull dedup (two callers pulling the same model
simultaneously is not guarded against), auto-pulling a model when a
meeting starts, changing the M3 translator wiring itself.

## Acceptance criteria

1. `task build && task test && task lint` pass; every new test uses a
   fake Ollama HTTP server (httptest) — no real Ollama, no real network.
2. `TestListModelsReachable` — fake `/api/tags` returns two models;
   `ListModels` returns their names.
3. `TestListModelsUnreachable` — no server listening (or one that
   refuses connections) at the given host; `ListModels` returns an error
   wrapping `ErrOllamaUnreachable`.
4. `TestPullStreamsProgress` — fake `/api/pull` writes several NDJSON
   lines then `{"status":"success"}`; `onProgress` is called once per
   line in order with the right `status` strings, and `Pull` returns nil.
5. `TestPullPropagatesError` — fake server's stream includes a line with
   a non-empty `error` field; `Pull` returns a non-nil error.
6. `TestTranslateStatusEndpoint` — HTTP test: with a fake Ollama server
   that has the live model installed but not the batch model, the JSON
   response has `installed: true`/`false` matching; with no server
   reachable, `ollama_reachable: false` and 200 (not an HTTP error).
7. `TestTranslatePullEndpoint` — HTTP test: valid `target` streams
   NDJSON progress through to the response body; invalid `target` is 400.
8. `TestTranslateTestEndpoint` — HTTP test: valid request returns
   `{"translated": "..."}` from a fake translator wired via the
   `newTranslator` seam; missing `text`/`target_lang` is 400; a
   translator error is 502.

## Decisions

- `ListModels` and `Pull` are free functions in `internal/translate`
  (matching the spec's signatures exactly), not methods on
  `OllamaTranslator` — they don't need a translator instance, just a
  host. Added in a new sibling file `internal/translate/ollama.go`
  since the existing `OllamaTranslator` lives in `translate.go`.
- NDJSON line-splitting for `Pull` uses `bufio.Scanner` over the
  response body (default line-oriented splitting), decoding each
  non-empty line as its own JSON object. This is enough to satisfy
  bufio's default 64KB per-line limit, which every real Ollama pull
  status line is far under.
- `onProgress` has no return value/error path — the spec's signature is
  `func(status string)`, so there's nothing for it to fail; if a
  caller-provided callback panics that's their bug, not `Pull`'s to
  guard against.
- `/api/translate/status` wraps the `ListModels` call in a
  `context.WithTimeout` of 5s (`translateStatusTimeout` in
  `internal/server/server.go`) so a hung/unreachable Ollama doesn't
  stall the status check for the default HTTP client timeout. `/pull`
  and `/test` don't get this treatment: a pull is expected to take a
  long time by nature (model downloads), and `/test` reuses whatever
  timeout behavior `newTranslator`'s underlying `Translate` already has
  (unchanged from M3).
- No new seam fields were added to `Server` for `ListModels`/`Pull`
  themselves — unlike `newEngine`/`newTranslator`, these already take
  `host` as a plain parameter, so tests achieve hermeticity by pointing
  `cfg.Translate.Host` at an `httptest.Server` rather than by injecting
  a fake constructor. `newTranslator` (existing seam) is reused as-is
  for `/api/translate/test`.
- Invalid `target` on `/api/translate/test` (anything other than
  `"live"`/`"batch"`, after defaulting empty to `"live"`) returns 400,
  same as `/api/translate/pull` — the spec only calls this out
  explicitly for `/pull`, but the same validation and status code is
  the simplest consistent behavior for `/test`, which takes an
  identical `target` field.
- `/api/translate/pull`'s error frame on a `Pull` failure mid-stream
  uses the same JSON shape as a progress frame's sibling case
  (`{"error": "..."}`), written and flushed once, matching the spec's
  wording exactly; no HTTP trailer or status-code signal is used since
  headers are already committed by the time streaming starts.
