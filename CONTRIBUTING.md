# Contributing to CatchM

## Branching model

- **`develop` is the only integration branch.** Base your feature/fix
  branch on `develop` and open your PR against `develop`.
- **`master` is a read-only pointer to the latest release.** A workflow
  fast-forwards it to each release tag after the release workflow
  succeeds. Never open PRs against it and never commit to it directly.
- **Don't push tags by hand.** Release tags are created by the
  `tag-release` workflow (see the release runbook below). A hand-pushed
  `v*` tag would bypass validation and trigger the full publish —
  GitHub release plus the R2 update manifest that shipped clients
  auto-update from at runtime.

## Conventional Commits

PR titles should follow [Conventional Commits](https://www.conventionalcommits.org/)
(`feat:`, `fix:`, `chore:`, `docs:`, ...) — the merge commits land as
`Merge #N: <title>`, and a tidy conventional title keeps history
readable. (Unlike release-please setups, nothing here *depends* on the
format: release notes are generated by GitHub from PRs and commits.)

## Local development

```
task build   # Go binary + embedded web UI
task test    # go test ./...
task lint    # go vet + gofmt check
task run     # the daemon (catchm serve)
```

Desktop shell (needs the [wails](https://wails.io) CLI, pinned to
go.mod's `wailsapp/wails/v2` version; the Windows installer also needs
NSIS, the macOS `.dmg` an Apple Silicon Mac):

```
task desktop:dev
task desktop:build
task desktop:release VERSION=1.2.3 UPDATE_BASE_URL=https://catchm-api.spacingmind.com/update         # Windows installer
task desktop:release:darwin VERSION=1.2.3 UPDATE_BASE_URL=https://catchm-api.spacingmind.com/update  # macOS arm64 .dmg
```

The macOS build is unsigned (ad-hoc signature only) and has no tray
icon. A tray library can't coexist with Wails v2 on macOS; see
`cmd/catchm-desktop/tray_start_darwin.go`.

## Release runbook

From "code merged on develop" to "shipped clients updating
themselves" — one human decision, everything after it validated:

1. **Cut the tag**: Actions → `tag-release` → Run workflow on
   `develop`, with the version (`x.y.z`, no `v`, no pre-release
   suffix). Leave `dry_run` on for a rehearsal — it validates and
   creates the tag locally, pushing nothing.
2. **What it validates**: plain `x.y.z` (NSIS's `VIProductVersion`
   rejects anything else — and the tag is public before the build
   runs, so this must not slip through), strictly greater than the
   latest existing tag (re-releasing would overwrite R2 objects a
   client may be mid-download), and the tag must not already exist.
   The tag is annotated, authored by `github-actions[bot]`, pointed at
   `origin/develop` HEAD, and pushed alone (never `--tags`).
3. **`tag-release` then dispatches `release.yml` on the tag.** A tag
   pushed with `GITHUB_TOKEN` can't trigger workflows itself, so the
   dispatch replaces the push trigger (`dry_run=false`, same result).
   Two jobs build in parallel: `windows` (the NSIS installer, `task
   desktop:release`) and `macos` (`macos-14`, the arm64 `.dmg`, `task
   desktop:release:darwin`), each with a SHA-256 checksum. Only when
   both succeed does `publish` attach all four files to the GitHub
   release, build `latest.json` listing all four, and upload everything
   to the catchm-releases R2 bucket. `latest.json` goes last, so a
   half-uploaded release is never advertised. That R2 manifest is
   what shipped clients actually poll (`catchm-api`'s `/update`
   route); the GitHub release is the public record. Each client picks
   its own platform's assets from the manifest. Windows installs
   in-app; macOS opens the `.dmg` download in the browser.
   **The Worker's download route allowlists asset names**: a new asset
   name must be deployed to catchm-api before the first release that
   publishes it, or those downloads 404.
4. **After `release.yml` goes green**, `tag-release` fast-forwards
   `master` to the tag. If `release.yml` fails, `master` stays put —
   the tag/release are still published (fix forward with a new
   version, never re-tag).

### Dry runs

- `tag-release` with `dry_run` (default): validation + local tag only.
- `release.yml` also has a `workflow_dispatch` with its own `dry_run`
  (default true): builds + checksums both platforms and uploads them as
  workflow artifacts, skipping the GitHub release, manifest, and R2
  upload. It can run on any branch (`gh workflow run release.yml --ref
  <branch> -f dry_run=true -f version=x.y.z`), which validates build
  changes before they merge.

### What a release must never do

- Ship with updates silently off: `desktop:release` refuses an empty
  `UPDATE_BASE_URL`, and `release.yml` fails the build if the
  `UPDATE_BASE_URL` repo variable is missing.
- Publish a manifest that lies about asset sizes: `release.yml` reads
  sizes off the built files, not from earlier steps.
- Overwrite `latest.json` before its assets exist: R2 upload order puts
  the manifest last.

## Why not release-please / a release branch?

Surveyed goreleaser (single branch + bot-pushed tags, releases
authored by `github-actions[bot]`) and syncthing (bot tags a release
branch, but only because it maintains parallel backports). A
release-only `master` merge target needs sync-back guard machinery
(see this org's smind repo) to avoid clobbering release metadata — a
failure mode a single integration branch can't develop in the first
place. Full reasoning: `docs/plans/completed/release-process.md`.
